The short version

I don't keep a list of allowed and banned tasks. I ask one question: can this be undone? If yes, AI gets a long leash. If no, the decision is mine, every time.

The question I get asked most about this project isn't "what did you build." It's "wait, you let AI do what?" Fair. The honest answer is a lot more than people expect and a lot less than people fear, and the line between the two isn't drawn by task type. It's drawn by one question.

The only rule that matters

Can this be undone?

That single distinction does more work than any list of allowed and disallowed tasks, because it scales. New situations come up constantly in a project like this. Instead of writing a new rule for each, I ask the same question.

Provisioning something new, drafting a doc, proposing a design, running a check, spinning up a container that doesn't touch anything live. AI can just go.

  • A new container gets provisioned, configured and brought up to the project's standards without me typing a command.
  • A first draft of how a new service should sit behind the reverse proxy and identity layer gets written before I've thought about it.
  • Docs and trackers stay current as a side effect of the work, not as a separate chore.

None of that touches anything that currently works. That is what makes the leash safe to extend.

Anything that touches the existing, working homelab, anything that deletes or overwrites, anything involving credentials, any call on architecture that's already settled. Not "AI drafts it and I rubber-stamp it." Mine, deliberately.

  • Nothing gets deleted, disabled or overwritten on the running homelab without me explicitly saying go.
  • Credentials and tokens are never held by AI between sessions. They're provided fresh, used, and gone.
  • A proposal that touches something we already settled, like an architecture decision or an access policy, is a conversation, not an execution.

Access is a design decision

This only works because access itself was scoped on purpose. AI in this project can reach the actual hypervisor: SSH in, provision containers, work inside them. That is real infrastructure access, not "helped me write a script I then ran myself." Real access is what made the reversible/irreversible rule non-negotiable. The more capable the access, the more that one rule has to hold.

Why this beats either extreme

The two failure modes are obvious in hindsight. Give AI no real access and you've built a slower version of copy-pasting from a chat window: all the thinking, none of the leverage. Give it unscoped access and you're one confidently wrong suggestion away from a bad night.

The playbook is wide open on anything that can be undone and tight on anything that can't. That turns out to cover almost everything a homelab needs, most of the time, without me being in the loop for all of it.
